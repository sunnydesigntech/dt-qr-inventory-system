1 · Audit of the existing system

The current code.gs renders three coupled but distinct surfaces from one HtmlService template, which is the right architectural choice for an Apps Script web app but creates a few visual problems worth fixing in this pass:

  • Landing, Storage page, and Technician mode share styles but communicate mode poorly. Today a technician opens the same chrome they were just reading from — the only signal that they can edit is a button. After a QR scan, the user does not always know which room or storage they are looking at until they read body copy.
  • Chemical hazards appear as inline text remarks. There is no consistent visual marker, and the safety affordance is buried in the Remarks column of the inventory sheet.
  • Empty storages exist by design (the rollout workflow imports the storage master before items), but visually they look like a broken page. Technicians should see an intentional empty state, not a void.
  • Readiness ships as an Inventory_Readiness_Report sheet. Useful for the developer; opaque for anyone else. The web app can surface a single number ("data readiness 86 / 100") without rebuilding the report.
  • QR labels render as a print sheet but lack the room context, hazard tag, and storage ID hierarchy that a technician scans visually before scanning digitally.
  • Failure modes (no SPREADSHEET_ID, missing WEB_APP_BASE_URL, malformed ?room=&loc=) currently fall through to plain text or a half-rendered page. Each deserves an explicit screen.

The fix in this prototype is not to rewrite the runtime, only the rendered HTML/CSS — every screen here can be produced by the existing doGet(e) by adding template branches and a token-based stylesheet.

2 · Design principles

Scan, then act

The most common entry point is a phone camera pointed at a printed sticker. The first thing a technician needs to know on arrival is: am I in the right place. Every storage page therefore opens with the room → storage → ID hierarchy in that order, before any list of items.

One mode at a time

View Mode and Tech Mode share the same skeleton but never the same chrome. Tech Mode adds a warm tinted background, a sticky save bar, and per-row controls. The colour shift is subtle but unambiguous: a technician who pulled up the wrong URL will notice within a glance.

Hazards travel with the item, not the cabinet

Glassware lives next to flammables in some D&T storage cupboards. Marking the entire cabinet "hazardous" is incorrect. Hazard signalling lives on the item card, not the storage card.

Static markup, no SPA

Every screen here is a single round-trip HtmlService render. No fetch, no router, no client-state library. Tech Mode posts back through google.script.run; a save returns a fresh page.

5 · Component specs

Storage card (landing list)

  • Min height 88px, padded 16px, radius 16, border 1px --line.
  • Left rail 4px wide, coloured by hazard (red) or rollout (teal); transparent otherwise.
  • Title is the storage label. Eyebrow above it shows the room. Sub-line shows the location detail (shelf 2, drawer A) in muted ink.
  • Trailing tile shows the count of expected items in display/lg; below, a small status dot row indicates Good / Low / Missing in aggregate.
  • Tap target is the entire card. No nested links.

Item card

  • Two columns: identity left, expected qty + status right.
  • Identity column shows: item name (15/600) with optional hazard pill, ID + category + unit in 11.5/400 muted, optional remarks in 12.5/400.
  • In Tech Mode the right column collapses to a quantity stepper (− / input / +) and a status select.
  • Changed rows gain an amber left border (#f59e0b) and an inline diff line: "Changed · 12 → 10".

Mode badge

Top-right of every storage page. View for read-only, Tech for technician mode. The same component drives the page background tint via a data-mode attribute on the body.

Sticky save bar

  • Pinned to bottom of the viewport, full width, 64px tall.
  • Left: count of unsaved changes ("3 unsaved changes" in amber when dirty, "No changes yet" muted otherwise).
  • Right: primary action Save updates. Disabled with opacity:.6 when clean.
  • Reveals only in Tech Mode. Page padding-bottom must be ≥ 96px while the bar is visible to avoid covering the last row.

6 · Screen specs

Landing

  1. Brand block (VSA wordmark + "Design & Technology · Inventory").
  2. Search input, full width, sticky after scroll.
  3. KPI strip: 3 tiles — locations, items, chemicals.
  4. Rollout banner (only when rollout419A.pct < 100).
  5. Room sections: Room 419A · D&T Studio, Room 419 · Workshop, ordered by rollout state then alphabetical. Each section header is sticky-on-scroll.
  6. Storage cards within each section, virtualised by category (Cabinet, Tool board, Drawer, Chemical).

Storage · View Mode

  1. Context strip: back arrow · room eyebrow · storage label · specific location · mode badge.
  2. Pill row: ID (mono), short code, count, hazard count, attention count.
  3. Search input + status filter (single line).
  4. List of item cards. Hazard items pinned to top when hazardTone = section, otherwise sorted by ID.

Storage · Tech Mode

Same layout. Background tint #fffbeb. Right column of every item card swaps to controls. Sticky save bar appears.

Admin · Readiness

Single screen, four blocks: gauge (score / 100), six issue tiles, 419A rollout panel with progress bar, diagnostics list. Designed to print well to A4 if the school wants a paper copy alongside the spreadsheet report.

QR Labels · print preview

Two-column A4 grid, 8 labels per page. Each label: QR glyph + room eyebrow + storage label + specific + ID badge + optional hazard line. The print stylesheet hides the toolbar and prints labels at 100% scale.

Diagnostics

Four error variants — missing spreadsheet ID, missing base URL, no matching ?loc, save bridge unavailable. Every variant explains what, why it matters, how to fix, and ends with the diagnostics list so the developer does not need a second tool.

7 · Chemical hazard treatment

Five options exposed in Tweaks; pick one and ship it. The default is Badge: a small red "HAZARD" pill next to the item title. It is the least visually disruptive option that still passes a five-foot test on a phone screen.

  • Badge — pill on the title row. Default. Works on any item count.
  • Stripe — diagonal red hatching on the card border. High visibility, but noisy in a long list.
  • Band — solid red top band on the card. Good for chemical-heavy storages, not mixed lists.
  • GHS diamond — small red diamond glyph after the title. Most accurate to lab convention; relies on user familiarity.
  • Section — pin all hazards to a top group with an "Chemical hazards · pinned" header. Best for storages where hazards are exceptional.

Recommendation. Use Badge on individual storages, and Section only on the few storages that mix glassware with reagents. Avoid Stripe at scale — when ten of twelve items are hazardous the page becomes one red block and the signal is lost.

9 · Apps Script integration notes

Architecture constraint

Per the repo README, runtime code stays in code.gs. That includes the rendered HTML, CSS, and inline JS for save handlers. Splitting into .html partials is allowed in development via clasp's local files but the deployed pushed file must remain a single Apps Script file.

Routing

The current doGet(e) branches on e.parameter.room, e.parameter.loc, and e.parameter.mode. Add three more branches:

  • ?view=admin → Readiness screen (existing Create Readiness Report data, summarised).
  • ?view=labels → Print preview of QR Label Sheet.
  • ?view=diag&kind=… → Diagnostics screen, used for soft errors.

Token CSS injection

Render the token :root block from a constants object so the developer can re-tune colours without a full edit pass:

const TOKENS = {
  ink: '#0f172a', brand: '#1d4ed8', hazard: '#b91c1c',
  rollout: '#0d9488', techBg: '#fffbeb'
};

function renderTokens_() {
  return Object.entries(TOKENS)
    .map(([k, v]) => `--${k}:${v};`)
    .join('');
}

11 · Out of scope · next steps

  • Offline queue. Tech Mode currently assumes a live save round-trip. A queue persisted in localStorage would let technicians work in basement rooms without LTE.
  • Multi-room rollout. Today the rollout panel is hard-coded to 419A. Once the second room ships, this becomes a per-room block on the readiness screen.
  • Audit trail. Every save should append a row to a Inventory_Audit sheet with timestamp, email, item, before, after. Surface in admin.
  • Photo upload. Damaged-item flagging is more useful with a photo. Apps Script can accept a base64 blob via google.script.run and write it to Drive.
  • Search across rooms. The landing search currently scopes to storages. A second mode that searches items globally is a small change on the server but a different UI surface.

End of spec. Open the prototype side-by-side; every component above is rendered in the live HTML for direct measurement and copy-paste.
